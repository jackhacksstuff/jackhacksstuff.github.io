// Overview

HeartBleed is a single-flag room built around CVE-2014-0160, the OpenSSL bug that broke the internet in 2014. The entire objective is to confirm the vulnerable service and pull the flag out of leaked server memory. It's a short box, but the vulnerability behind it is one of the most consequential in modern computing, which makes it a great one to understand properly rather than just run a scanner against.

// Background: What Is HeartBleed?

HeartBleed lives in the TLS Heartbeat extension (RFC 6520), which lets a client and server check that a connection is still alive without renegotiating the whole session. A heartbeat request carries a small payload and a claimed length field describing how big that payload is.

The flaw: vulnerable OpenSSL versions trusted the claimed length without checking it against the actual payload size. Send a heartbeat claiming 64KB while supplying 1 byte, and the server reads 64KB starting just past your payload straight out of its own process memory and echoes it back. That's it. Just a slow drip of whatever happens to be in memory: session cookies, credentials, form submissions, and occasionally private key material.

Affected: OpenSSL 1.0.1 through 1.0.1f (and 1.0.2-beta). Patched in 1.0.1g. The bug was independently discovered by Neel Mehta of Google and by Codenomicon, who coined the name and launched the now-famous logo.

// Reconnaissance

Confirming the Vulnerability

There's no need for a full port sweep here. The target is a web service, so a targeted Nmap script against 443 is the fastest confirmation:

$ nmap -p 443 --script ssl-heartbleed <target_ip>

PORT    STATE SERVICE
443/tcp open  https
| ssl-heartbleed: 
|   VULNERABLE:
|   The Heartbleed Bug is a serious vulnerability in the popular OpenSSL cryptographic software library...
|     State: VULNERABLE
|     Risk factor: High
|_      ...

The VULNERABLE state confirms the server is running an affected OpenSSL build and is responding to malformed heartbeats. No exploitation has happened yet, the script just probes and reports.

// Exploitation: Leaking Memory with Metasploit

You can hand-roll a heartbeat packet in Python or Scapy, but Metasploit ships a dedicated auxiliary module that handles the malformed requests and dumps the leaked memory for you. For a learning box, that's the right tool. It keeps the focus on interpreting the leak rather than reimplementing the TLS handshake.

$ msfconsole
msf6 > use auxiliary/scanner/ssl/openssl_heartbleed
msf6 auxiliary(scanner/ssl/openssl_heartbleed) > set RHOSTS <target_ip>
msf6 auxiliary(scanner/ssl/openssl_heartbleed) > set VERBOSE true
msf6 auxiliary(scanner/ssl/openssl_heartbleed) > run

VERBOSE true is the important setting. Without it you get a "vulnerable" confirmation but not the leaked bytes printed to the console. With it, you get a stream of mostly binary noise, punctuated by readable chunks of memory.

Why this is probabilistic: each heartbeat request over-reads a different region of process memory. The flag won't necessarily be in the first dump. Run the module a few times and watch the console output until a readable chunk surfaces. That's what this one took: a handful of runs before the flag appeared.

// Finding the Flag

Buried in the leaked memory was a full HTTP request body from a previous visitor to the application, including form fields and, sitting right in the middle of them, the flag. It showed up in the Metasploit output as readable text among the binary noise:

Content-Length: 75
Content-Type: application/x-www-form-urlencoded

user_name=...&user_email=...&user_message=[redacted]

The flag is in the standard THM{...} format, embedded inside a URL-encoded form body. That's the whole room.

Other Artefacts in the Leak

The dump also contained chunks of the server's X.509 certificate, C=UK, L=London, O=TryHackMe, CN=localhost, with a validity window from 2019 to 2020. That's the public cert, so not sensitive on its own, but it's a useful reminder of what HeartBleed can expose. With enough requests you can leak private key material, which is exactly why the bug was treated as a catastrophe for real-world TLS services.

Why this works: HeartBleed is a read primitive, not a code-execution primitive. You don't get a shell from it, you get whatever the process has recently handled. On a real target that's session tokens and credentials; on this box it's a deliberately planted form submission. The lesson generalises: memory disclosure bugs turn unrelated users' data into an attacker's data.

// Verdict

HeartBleed is a very short box: recon, one Metasploit module, and reading the output. As a CTF it's almost trivially easy. As a lesson, though, it's worth doing properly: the value is in understanding the heartbeat over-read, why the leak is probabilistic, and what a memory-disclosure bug actually hands an attacker. If you've ever wondered why "just patch OpenSSL" became a company-wide emergency in 2014, this room is the hands-on version of that answer.

→ 6/10 — mechanically easy, historically important. Do it once to internalise CVE-2014-0160, then move on.
